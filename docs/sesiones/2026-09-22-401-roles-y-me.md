# 2026-09-22 — Roles empresariales e identidad de sesión

## Qué se hizo

- `UserRole` pasó a `SUPER_ADMIN`, `EMPRESARIO`, `EMPRESA_ADMIN` y
  `EMPRESA_OPERATOR`. La migración renombra los dos valores anteriores y suma
  `EMPRESARIO`, por lo que conserva todas las filas.
- Se actualizaron autenticación, guardas internas, seeds, trazabilidad y
  fixtures. `EMPRESARIO` conserva el acceso empresarial que tenía la cuenta
  administradora; `SUPER_ADMIN` conserva el acceso interno transversal.
- `GET /me` publica `id`, `email`, `rol` y `empresaId`; el contrato OpenAPI
  quedó en 33 operaciones tipadas.
- Se agregó una prueba PostgreSQL de la migración: dos filas anteriores se
  mapean sin cambiar el conteo y un valor desconocido falla fuerte.

## Decisiones que tomé sobre la marcha

- **Qué decidí:** usar `ALTER TYPE ... RENAME VALUE` para los dos roles
  existentes. **Qué otra opción había:** crear un enum nuevo, castear la columna
  y borrar el anterior. **Por qué elegí esta:** renombrar conserva las filas y
  evita una migración destructiva (Constitución §9 y DOM-06).
- **Qué decidí:** `empresaId` es `null` para `SUPER_ADMIN` o cuando no existe
  empresa/membresía; para cuentas empresariales se toma la primera relación
  activa en orden estable. **Qué otra opción había:** devolver un id inventado o
  cambiar el contrato a una lista. **Por qué elegí esta:** el issue pidió un
  campo singular y dejó la vista multiunidad fuera de alcance; la ausencia se
  declara (Constitución §2) y se mantiene la compatibilidad documentada en ADR
  0029 de #389.
- **Qué decidí:** conservar `ADMIN` sólo como bucket contable interno del
  clasificador de nómina. **Qué otra opción había:** renombrarlo junto con el
  rol de usuario. **Por qué elegí esta:** no es un `UserRole`; representa gastos
  de administración y cambiarlo mezclaría dos dominios distintos.

## Dónde el issue no alcanzaba

- No definía cómo elegir `empresaId` si una cuenta posee varias empresas. Se
  mantuvo la primera activa y estable hasta el issue futuro de vista
  consolidada, que el propio #401 deja fuera.
- El repo no tenía una guarda literal `requireRole('COSTISTA')`; la condición
  empresarial concreta estaba en telemetría. Se extendió esa autorización a
  `EMPRESARIO` y se agregó una prueba HTTP, sin ampliar otros permisos.
- La prohibición textual de los roles anteriores convive necesariamente con el
  SQL de migración y su prueba. La guarda revisa código vigente, schema, tests,
  seeds y OpenAPI; el fixture arma los valores anteriores por partes y las
  migraciones históricas permanecen inmutables.

## Qué quedó afuera

- Autorización sectorial y CRUD de cargadores (#387).
- Vista consolidada multiunidad de `EMPRESARIO`.
- Pantallas de frontend (#184, #187 y #190).
