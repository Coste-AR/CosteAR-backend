## Qué se hizo

Se agregaron pruebas HTTP para `PUT /cost-structures/:id/raw-material` y
`PUT /cost-structures/:id/direct-labor`. Ambas envían una configuración vacía a las rutas reales,
con autenticación y handler de errores reales y Prisma simulado. Fijan que la validación responde
`400 VALIDATION_ERROR` y que no persiste la configuración.

## Verificación de falla

La primera ejecución esperó intencionalmente `422`; las dos pruebas fallaron al recibir `400`
(`expected 400 to be 422`). Eso demuestra que las aserciones miden el código de estado y no pasan
por defecto. Tras corregir la expectativa al contrato actual, las corridas fueron:

- Prueba nueva: 1 archivo, 2 pruebas en verde.
- `npm.cmd run test:http`: 13 archivos, 82 pruebas en verde.
- `npm.cmd run lint` y `npm.cmd run typecheck`: sin errores.
- Suite completa: 170 archivos en verde, 1 omitido; 1549 pruebas en verde, 4 omitidas.

## Decisiones tomadas

- **Decisión:** probar un payload vacío para ambas secciones.
- **Alternativa:** construir configuraciones casi válidas con un único campo inválido.
- **Motivo:** la configuración vacía alcanza la ruta, obtiene la estructura y falla en el schema de
  cada sección antes de cualquier escritura; fija el camino de error más directo sin añadir datos
  de dominio irrelevantes.

- **Decisión:** crear una suite HTTP separada.
- **Alternativa:** modificar la suite de #162.
- **Motivo:** el issue #170 completa dos rutas dinámicas omitidas del inventario anterior y deja su
  alcance, mocks y contrato trazables sin reescribir tests existentes.

## Dónde el issue no alcanzaba

No especificaba el código exacto. Se verificó el handler existente: los errores Zod se traducen a
`400 VALIDATION_ERROR`; no se inventó un contrato `422`.

## Fuera de alcance
