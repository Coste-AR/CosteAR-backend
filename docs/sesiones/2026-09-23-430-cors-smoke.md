# 2026-09-23 — El smoke pregunta desde dónde viene el navegador

## Qué se hizo

- Los dominios exactos `coste-ar.com` y `www.coste-ar.com` se permiten sin depender de la
  configuración de Railway; los dominios que sólo contienen ese texto siguen rechazados.
- Un origen rechazado conserva el warning operativo, pero ya no levanta una excepción ni responde
  500.
- El smoke post-deploy exige `FRONTEND_ORIGINS`, prueba un preflight real por cada origen y falla si
  el status no es 2xx o la cabecera no refleja exactamente el origen.
- El workflow corre también a diario contra staging, incluso cuando la configuración cambió sin un
  push de código.

## Decisiones que tomé sobre la marcha

- **Qué decidí:** centralizar la whitelist y el callback en una política CORS pura. **Qué otra
  opción había:** exportar funciones internas desde `app.ts` o duplicar el callback en el test.
  **Por qué elegí esta:** permite probar la coincidencia exacta y montar el mismo callback en un
  servidor HTTP mínimo sin inicializar Prisma, Redis ni Sentry.
- **Qué decidí:** en la ejecución programada hacer checkout explícito de `staging` y verificar su
  SHA real. **Qué otra opción había:** usar `github.ref_name` y `github.sha`, que en un `schedule`
  corresponden a la rama por defecto. **Por qué elegí esta:** el issue pide medir staging y `dev`
  no despliega ningún ambiente.
- **Qué decidí:** usar `process.exitCode` después de las consultas HTTP. **Qué otra opción había:**
  conservar `process.exit()`. **Por qué elegí esta:** el rojo ejecutable mostró que el cierre
  inmediato podía abortar libuv en Windows antes de drenar `fetch`; el código de salida sigue
  siendo 1 sin ocultar el diagnóstico.

## Dónde el issue no alcanzaba

- No definía qué rama toma una ejecución `schedule`; se eligió `staging`, el ambiente que el propio
  criterio pide vigilar diariamente.
- No indicaba si el smoke debía seguir probando CORS cuando el SHA aún no llegó. Se valida primero
  la versión y después CORS para no atribuirle al commit nuevo una respuesta del deploy anterior.
- La primera corrida completa tuvo un timeout aislado en `admin-stats` mientras inicializaba colas
  sin `DATABASE_URL`; el archivo pasó 2/2 aislado y la repetición completa quedó verde.

## Qué quedó afuera

- Cargar la variable externa de repositorio
  `FRONTEND_ORIGINS=https://coste-ar.com,https://costear-frontend.vercel.app`; debe hacerlo Santiago
  porque es configuración fuera del repo.
- La corrida manual real contra staging queda para después de que el cambio se promueva allí. No se
  promovieron ramas ni se modificó Railway o Vercel.
